2. ELABORATION OF DIFFERENCES BETWEEN EACH BENCHMARK
==============================================================================

2.1 CASE A vs. CASE B (ALGORITHMIC FORMULATION)
------------------------------------------------------------------------------
The Sandia ISx (Integer Sort eXtreme) specification defines two fundamental
problem classes for distributed integer sorting:

1. Case A (Structured Equal Buckets):
   - Key Property: Every chip generates an identical, strictly balanced number
     of keys targeted for every peer chip.
   - Routing: Communication is deterministic and static. Key data can be
     structured directly into a 3D/4D tensor layout:
       `(TILES_PER_BUCKET, NUM_CHIPS, KEYS_PER_TILE)`
   - Collective: Executes a standard, uniform `jax.lax.all_to_all` across the
     chip dimension (axis 1).
   - Downstream Sort: Because bucket boundaries are fixed and known ahead of
     time, each row of keys (1,048,576 keys = 8 MiB) fits 100% inside the on-chip
     128 MiB VMEM scratchpad. The sort is executed row-by-row on the VPU using
     a localized bitonic sorting network without inter-bucket spilling.

2. Case B (Unstructured Ragged / Unequal Buckets):
   - Key Property: Models real-world data skew. Keys are generated from a pure
     unstructured pseudo-random distribution. The top 3 bits determine the
     destination chip, creating stochastic, variable bucket sizes (e.g. Chip 0
     receives anywhere from 66,950,144 to 67,240,064 keys from different peers).
   - Routing: Dynamic and data-dependent. Requires a 2-stage communication protocol:
       Stage 1 (Metadata Exchange): Each chip computes a local histogram
               (`jnp.bincount`), shares send/recv sizes via an all-to-all,
               and computes memory offsets (`jnp.cumsum`).
       Stage 2 (Data RDMA): Variable-length blocks are transmitted using
               `jax.lax.ragged_all_to_all`.
   - Downstream Sort: Bucket sizes vary, so received data must be concatenated
     and sorted globally across the entire received buffer on each chip using
     a global VPU sort rather than independent row-level sorting.


2.2 SEQUENTIAL vs. PIPELINED (TRANSFER-WHILE-SORT)
------------------------------------------------------------------------------
1. Sequential Execution:
   - Phase 1 (KeyGen): Entire dataset (67.1 GB in Case A, 34.4 GB in Case B) is
     generated and materialized in HBM.
   - Phase 2 (Exchange): All-to-All collective transmits the entire dataset
     across the ICI network into receive buffers. During this phase, the VPU
     compute ALUs are completely idle.
   - Phase 3 (Sort): VPU streams through HBM to sort keys. During this phase,
     the optical ICI network interfaces and DMA controllers are completely idle.
   - Memory Implication: High peak memory footprint because input keys,
     transferred keys, and sorted keys coexist simultaneously in HBM.

2. Pipelined Execution (Transfer-While-Sort):
   - The total workload is subdivided into K = 8 pipeline stages (chunks).
   - In a double-buffered schedule:
       While Chunk (k+1) is being transferred across the ICI network via DMA,
       Chunk (k) is being sorted concurrently on the VPU,
       and Chunk (k+2) is being synthesized in on-chip VMEM via Pallas.
   - Memory Implication: Massive reduction in peak working memory. In Case B,
     live in-use memory dropped from 8.47 GiB to 0.11 GiB, and peak HBM usage
     dropped from 12.87 GiB (41.2%) down to 4.51 GiB (14.4%)—a 65% reduction!
   - Runtime Implication:
     * In Case A, communication takes ~0.10s while sorting takes ~2.13s (comm is
       only ~4.5% of total time). As a result, overlapping comm behind sort hides
       network latency completely, matching sequential runtime (~2.23s) while
       freeing up memory headroom for much larger datasets.
     * In Case B, pipelined chunking eliminates the 2 GiB DMA addressing limit
       and slashes memory by 65%, but incurs repeated global radix re-sorts
       over chunks, yielding a clean trade-off between memory footprint and latency.

3. DEEP HARDWARE ARCHITECTURE BREAKDOWN: TPU v6e (TRILLIUM) COMPONENTS
==============================================================================

This section details exactly what is occurring at each physical hardware component
of the Google TPU v6e architecture during the execution of both benchmarks.

+------------------------------------------------------------------------------+
| 3.1 HIGH BANDWIDTH MEMORY (HBM3) SUBSYSTEM                                   |
+------------------------------------------------------------------------------+
Hardware Architecture:
  - Each TPU v6e chip is equipped with 32.0 GiB of HBM3 memory (31.25 GiB usable
    by XLA), offering a peak aggregate memory bandwidth of 1,640 GB/s per chip.
  - HBM is organized into multiple independent pseudo-channels and managed by
    on-chip memory controllers with high-concurrency reordering buffers.

Component Activity During Benchmarks:
  1. Case A KeyGen Phase:
     - The Pallas kernel synthesizes high and low 32-bit components directly in
       on-chip VMEM vector registers ($v).
     - Upon kernel completion, the DMA write channels stream the 64-bit packed
       arrays into HBM at 619.6 - 693.1 GB/s cluster aggregate throughput.
     - HBM bandwidth utilization is ~5.3% of theoretical peak, indicating that
       KeyGen is strictly compute-bound by VPU PRNG hashing, not memory-bound.
  2. Case A Communication & Sort Phase:
     - Sequential: ICI DMA writes incoming 8.39 GB directly into contiguous HBM
       allocations. Once the collective completes, the VPU reads rows from HBM
       into VMEM, executes bitonic sort, and writes sorted rows back to HBM.
       This generates ~102 GiB of read/write HBM traffic per chip.
     - Pipelined: The ICI DMA actively writes Chunk (k+1) into HBM while the
       VPU simultaneously streams Chunk (k) from HBM for sorting.
       This introduces memory controller bus arbitration contention: simultaneous
       streaming writes from ICI DMA channels and streaming reads from VPU
       burst access compete for the 1,640 GB/s HBM channels, explaining why
       pipelined execution runs at ~2.236s vs 2.233s sequential.
  3. Case B Dynamic Allocation & Memory Footprint:
     - Sequential Case B buffers the entire 4.29 GB raw dataset, plus 4.51 GB of
       receive buffers (including 10% safety padding), peaking at 12.87 GiB (41.2%).
     - Pipelined Case B processes 512 MiB chunks iteratively, deleting finished
       arrays immediately. Live in-use HBM drops to 0.11 GiB, and peak usage
       drops to 4.51 GiB (14.4%), leaving 26.74 GiB of free HBM headroom!


+------------------------------------------------------------------------------+
| 3.2 DIRECT MEMORY ACCESS (DMA) ENGINES                                       |
+------------------------------------------------------------------------------+
Hardware Architecture:
  - TPU v6e contains dedicated hardware DMA engines that operate autonomously
    from the main compute units.
  - The DMA engines handle:
      a) Host-to-Device (PCIe / network) transfers.
      b) VMEM-to-HBM and HBM-to-VMEM internal 2D/strided block transfers.
      c) HBM-to-ICI and ICI-to-HBM network serialization/deserialization.

Component Activity During Benchmarks:
  1. Asynchronous Collective Offloading:
     - When `--xla_tpu_enable_async_all_to_all=true` is enabled, XLA lowers
       communication into non-blocking pairs: `all-to-all-start` and
       `all-to-all-done`.
     - The XLA Latency-Hiding Scheduler (LHS) programs DMA descriptors into the
       TPU command queue, allowing the ICI DMA engine to stream packets across
       the optical links in the background without stalling VPU execution pipelines.
  2. Case A DMA Patterns:
     - 512 DMA ops in sequential mode; 2,585 async start/done ops in pipelined mode.
     - Because Case A utilizes the zero-copy layout `(TILES, CHIPS, KEYS)`, the
       DMA engine reads contiguously across destination chips and writes into
       strided receive buffers, eliminating the need for an 8.4 GB out-of-place
       HBM memory copy (`jnp.swapaxes`).
  3. Critical Hardware DMA Constraint (2 GiB Addressing Limit):
     - In TPU v6e libtpu / XLA, `ragged_all_to_all` translates tensor row/block
       indices into byte addresses using signed 32-bit integers.
     - The maximum addressable byte offset for signed 32-bit arithmetic is:
         2^31 - 1 = 2,147,483,647 bytes (~2.0 GiB).
     - At 8x scale (4.29 GB per chip), an un-chunked monolithic transfer causes
       address overflow and integer wrap-around at exactly 2 GiB.
     - Pipelined execution breaks the transfer into 512 MiB chunks (<< 2 GiB),
       completely circumventing the hardware boundary and enabling seamless
       scaling to tens of billions of keys.


+------------------------------------------------------------------------------+
| 3.3 TENSORCORE: VECTOR PROCESSING UNIT (VPU) vs. MATRIX MULTIPLY UNIT (MXU)  |
+------------------------------------------------------------------------------+
Hardware Architecture:
  - A TPU v6e TensorCore consists of two primary compute engines:
      a) Matrix Multiply Unit (MXU): Systolic array engines specialized for
         dense matrix-matrix multiplications ($C = A \times B + C$) in bfloat16,
         float32, and int8.
      b) Vector Processing Unit (VPU): High-throughput 2D SIMD vector processors
         with dedicated 32-bit vector registers ($v0..$v31), scalar registers
         ($s0..$s15), and 128 MiB of on-chip Vector Memory (VMEM) scratchpad.

Component Activity During Benchmarks:
  1. MXU Utilization = EXACTLY 0.0% (Zero Matrix Operations):
     - The low-level HLO/LLO disassembly confirms: `dot / convolution = 0`.
     - Integer sorting, PRNG hashing, dynamic bincounting, and bitwise permutations
       contain zero matrix multiplies. The MXU systolic arrays remain completely
       quiescent throughout all benchmark runs.
  2. VPU Is the Primary Compute Engine (100% of Workload):
     - KeyGen Phase: VPU ALU executes PRNG hashing (Murmur3/splitmix style)
       using 12 to 18 integer bitwise operations per key (XOR, right shift,
       32-bit multiplication with golden ratios `0x85ebca6b` and `0xc2b2ae35`).
       Achieves 135.5 - 151.6 GOPS/s/chip in Case A, and up to 895.75 GB/s in Case B.
     - Sort Phase: VPU executes bitonic sorting networks using vector compare-
       and-swap instructions (vector select, vector min/max) across registers.
       Achieves 98.6 GOPS/s/chip sustained sorting rate.
  3. Register Architecture ($v0..$v31 Constraints):
     - The TPU v6e vector registers are strictly 32-bit wide.
     - Attempting native 64-bit arithmetic in Pallas throws:
         `NotImplementedError: 64-bit types are not supported`
     - Our benchmark overcomes this by generating separate high and low 32-bit
       components in VMEM vector registers and fusing 64-bit reconstruction at
       the JAX XLA boundary without spilling to HBM.


+------------------------------------------------------------------------------+
| 3.4 SPARSECORE SUBSYSTEM ANALYSIS                                            |
+------------------------------------------------------------------------------+
Hardware Architecture & Context:
  - In certain Google TPU architectures (such as TPU v4 and TPU v5p), Google
    integrated dedicated "SparseCore" (SC) accelerator units.
  - SparseCore is a memory-near, power-efficient architecture designed specifically
    to accelerate sparse embedding lookups, ragged gathers, and scatter-reduce
    operations in Deep Learning Recommendation Models (DLRM).
  - SparseCores have their own small vector cores, local SRAM scratchpads, and
    direct interfaces to the memory controllers to execute irregular memory
    accesses without thrashing the main TensorCore caches.

SparseCore Status on TPU v6e (Trillium):
  - TPU v6e (Trillium) is engineered as an ultra-high-density, cost-optimized
    accelerator focused on generative AI, LLM pre-training/inference, and dense
    VPU/MXU operations.
  - TPU v6e does NOT incorporate standalone SparseCore units (or they are not
    exposed for general-purpose XLA integer computation).
  - How Sparse Operations Are Handled on TPU v6e:
    * In Case B (Ragged Buckets), irregular dynamic binning and scatter operations
      are handled directly on the Vector Processing Unit (VPU) via `jnp.bincount`
      and `jnp.argsort` vector permutations, while irregular network movement
      is offloaded to the ICI DMA subsystem via `ragged_all_to_all`.
    * This demonstrates that the TPU v6e VPU + ICI DMA subsystem can efficiently
      emulate sparse/ragged scatter-gather sorting workloads even without
      dedicated SparseCore silicon.


+------------------------------------------------------------------------------+
| 3.5 INTER-CHIP INTERCONNECT (ICI) & NETWORK PACKET SIZING                   |
+------------------------------------------------------------------------------+
Hardware Architecture:
  - The TPU v6e Inter-Chip Interconnect (ICI) is a direct, low-latency, high-
    bandwidth optical/electrical network that connects chips into a multi-
    dimensional torus or mesh topology without external Ethernet switches.
  - In the `mb-tpu-v6e-multi-8` nodepool, the 8 chips form a 2x4 mesh/torus:
      * 2 nodes, each containing 4 TPU chips.
      * Intra-node chips connect via high-speed electrical traces.
      * Inter-node links connect via optical transceiver interfaces.
      * Peak theoretical bandwidth per link is ~400 Gbps.

The 4-Tier Network Packet Sizing Hierarchy:
  Data transmission across the TPU ICI fabric operates on a strictly tiered
  hierarchy:

  1. Tier 1: Hardware ICI Flit (Flow Control Unit) — 128 Bytes:
     - The atomic physical and link-layer packet unit of the TPU ICI network.
     - Every optical transceiver and router crossbar transmits data in 128-byte
       credits. Link-level error detection (CRC) and flow control operate per-flit.

  2. Tier 2: Benchmark Transfer Block (BLOCK_WIDTH = 128 uint64) — 1,024 Bytes:
     - Software grouping: 128 uint64 keys * 8 bytes = 1,024 bytes (1 KiB).
     - Bitcast representation: 256 uint32 keys * 4 bytes = 1,024 bytes.
     - EXACT HARDWARE ALIGNMENT:
         1 Benchmark Block = 1,024 bytes = EXACTLY 8 HARDWARE FLITS (8 * 128 B).
     - Aligns directly with TPU DMA burst write boundaries, preventing tail
       fragmentation or partial-flit padding.

  3. Tier 3: Pallas VMEM Compute Tile (TILE_BLOCKS = 1,024) — 1.0 MiB:
     - Tile Shape: 1,024 blocks * 128 keys = 131,072 uint64 keys.
     - Tile Footprint: 131,072 * 8 bytes = 1,048,576 bytes = 1.0 MiB = 8,192 Flits.
     - A 1.0 MiB tile consumes < 1% of the 128 MiB VMEM scratchpad, leaving
       ample space for double-buffering without spilling to HBM.

  4. Tier 4: Pipeline Chunk Buffer (TILES_PER_CHUNK = 512) — 512 MiB:
     - Keys per Chunk: 512 tiles * 131,072 keys = 67,108,864 keys (512 MiB).
     - Flits per Chunk: 4,194,304 hardware flits.
     - Streams continuously across ICI DMA while the preceding chunk sorts on VPU.


+------------------------------------------------------------------------------+
| 3.6 JAX ALL-TO-ALL vs. RAGGED ALL-TO-ALL SUBSYSTEM                           |
+------------------------------------------------------------------------------+
1. `jax.lax.all_to_all` (Case A):
   - Semantics: Fixed, symmetric data exchange where each chip sends exactly
     $N / P$ elements to each of the $P$ chips.
   - Lowering: Lowers directly to XLA HLO `all-to-all` instruction.
   - Hardware Implementation: Transmitted via fixed DMA descriptor chains.
     Because send/recv buffer addresses and offsets are static, XLA can schedule
     it with zero runtime coordination overhead.
   - Optimization: Executed on axis 1 (`split_axis=1, concat_axis=1`), enabling
     instant zero-copy reshaping for row-level bitonic sorting.

2. `jax.lax.ragged_all_to_all` (Case B):
   - Semantics: Variable-length, dynamic all-to-all collective where send sizes
     and receive sizes differ across peers and across iterations.
   - Lowering: Lowers to XLA HLO `ragged-all-to-all` custom call.
   - Hardware Implementation: Requires dynamic DMA scatter/gather descriptors.
     Each chip provides `input_offsets`, `send_sizes`, `output_offsets`, and
     `recv_sizes`.
   - Critical Lowering Workaround:
     * TPU XLA lacks an explicit 64-bit rewriter for `ragged_all_to_all`, causing
       lowering failures on uint64 tensors.
     * Solution: We perform a zero-copy bitcast to uint32 (`.view(jnp.uint32)`),
       doubling the inner dimension to 256 elements (1,024 bytes). The DMA
       transfers the payload at full wire speed. After reception, `.view(jnp.uint64)`
       restores the exact 64-bit keys with 100% bit-precision.

4. ARCHITECTURAL RECOMMENDATIONS FOR FURTHER OPTIMIZATION
==============================================================================

Based on empirical profiling, HLO/LLO disassembly, and hardware telemetry from
the live cluster runs, the following concrete architectural recommendations
are provided for scaling and optimizing the Sandia ISx benchmarks on TPU v6e:

1. Double-Buffered Pallas-Native In-VMEM Bitonic Sorting:
   - Current State: Phase 2 currently calls `jnp.sort()`, which streams entire
     rows back and forth between HBM and VPU, generating ~102-119 GiB of HBM
     traffic per chip.
   - Recommendation: Write a custom Pallas TPU kernel that executes the full
     bitonic sorting network directly within the 128 MiB VMEM scratchpad.
     Because an 8 MiB row fits completely within VMEM, all 210 comparison stages
     can execute in on-chip SRAM without intermediate round-trips to HBM,
     cutting Phase 2 runtime by an estimated 2.0x – 2.5x.

2. Scale Problem Size to Full HBM Capacity (100 GB – 120 GB Scale):
   - Current State: Case A operates at 67.11 GB (50% HBM peak usage); Case B
     operates at 34.36 GB (41.2% HBM peak usage).
   - Finding: Between 15.6 GiB and 26.7 GiB of allocatable HBM is completely
     idle on every chip.
   - Recommendation: Scale Case A from `TILES_PER_BUCKET = 1000` to `1800`,
     increasing dataset volume to 15.10 billion keys (120.8 GB).
     Under pipelined execution, peak HBM will remain safe at ~17.6 GiB, proving
     that TPU v6e can sort over 15 billion integers on an 8-chip slice.

3. Asymmetric Pipeline Stage Sizing:
   - Current State: Pipelined benchmarks use K = 8 fixed-size chunks.
   - Finding: The prologue (Stage 0) experiences a cold communication delay
     before the VPU begins sorting.
   - Recommendation: Implement a tapered pipeline chunk schedule: make Stage 0
     small (e.g. 64 tiles) to start the VPU sorting pipeline almost instantly,
     then scale subsequent chunks to 128 or 256 tiles to maximize DMA burst
     efficiency.

4. Dynamic Histogram Fusion in Case B KeyGen:
   - Current State: In Case B, keys are generated to HBM, then re-read in
     Phase 2A to compute destination bucket histograms (`jnp.bincount`).
   - Recommendation: Compute the 8-bucket histogram counts on-the-fly inside the
     Pallas KeyGen kernel using atomic scalar increments in VMEM. Emit the
     send sizes alongside the keys, completely eliminating the Phase 2A
     histogramming pass.

5. Align All DMA Buffers to 1,024-Byte (8 Flit) Boundaries:
   - Finding: The optical ICI network operates in 128-byte flits.
   - Recommendation: Ensure all dynamic ragged bucket buffers are multiples of
     128 uint64 keys (1,024 bytes = 8 flits). This prevents hardware padding
     penalties and ensures 100% line-rate transmission across optical links.


+------------------------------------------------------------------------------+
| 4.1 BENCHMARK-SPECIFIC MAPPING & USE-CASE INVARIANCE ANALYSIS                |
+------------------------------------------------------------------------------+

Q1: ARE THESE RECOMMENDATIONS FOR EACH BENCHMARK? WHICH ONE IS FOR WHICH?
------------------------------------------------------------------------------
No, they are NOT generic blanket recommendations. Each recommendation directly
targets specific architectural bottlenecks unique to particular benchmarks and
execution models:

1. In-VMEM Double-Buffered Bitonic Sort:
   - TARGET BENCHMARKS:
     * PRIMARY: Case A Sequential (`case_a_equal_buckets_xprof.yaml`) and
       Case A Pipelined (`case_a_equal_buckets_transfer_while_sort_xprof.yaml`).
     * SECONDARY: Case B Pipelined (for per-chunk sorting stages).
     * NOT APPLICABLE TO: Case B Sequential global merge pass (multi-GB array
       exceeds 128 MiB VMEM limit).
   - WHY: Case A shapes data into (TILES, CHIPS, KEYS) where each row is exactly
     1,048,576 keys (8 MiB). The TPU v6e has 128 MiB VMEM SRAM per core. An 8 MiB
     row fits fully into VMEM, allowing all 210 bitonic sort stages to execute in
     on-chip SRAM without round-tripping to HBM.

2. Scale Problem Size to Full HBM Capacity (100 GB - 120 GB Scale):
   - TARGET BENCHMARKS:
     * PRIMARY: Case A Pipelined and Case B Pipelined.
     * SECONDARY: Case A Sequential (up to ~80-90 GB).
   - WHY: Telemetry showed 16.4 GiB idle HBM in Case A and 27.5 GiB idle HBM in
     Case B Pipelined (due to chunk buffer recycling). Scaling TILES_PER_BUCKET
     from 1,000 to 1,800 scales total keys to 15.10 billion (120.8 GB), maximizing
     hardware memory controller saturation.

3. Asymmetric / Tapered Pipeline Chunk Sizing:
   - TARGET BENCHMARKS:
     * EXCLUSIVELY: Case A Pipelined and Case B Pipelined.
     * NOT APPLICABLE TO: Case A Sequential or Case B Sequential (no pipelines).
   - WHY: The prologue (Stage 0) suffers from a cold network delay where VPU
     idles waiting for Chunk 0 DMA transfer. Making Stage 0 small (e.g. 64 tiles)
     starts VPU compute in ~9 ms, while subsequent stages scale up to 128-256
     tiles for peak DMA burst bandwidth.

4. Dynamic Histogram Fusion in Case B KeyGen:
   - TARGET BENCHMARKS:
     * EXCLUSIVELY: Case B Sequential and Case B Pipelined.
     * NOT APPLICABLE TO: Case A (symmetric equal buckets require no histogramming).
   - WHY: Case B currently writes keys to HBM, then reads them back to compute
     destination send sizes via `jnp.bincount()`. Fusing the 8-bucket counter
     directly into the Pallas PRNG KeyGen kernel eliminates this entire HBM read
     pass.

5. Align All Dynamic Ragged DMA Buffers to 1,024-Byte (8-Flit) Boundaries:
   - TARGET BENCHMARKS:
     * EXCLUSIVELY: Case B Sequential and Case B Pipelined.
     * NOT APPLICABLE TO: Case A (tiles are already 1.0 MiB / 8,192 flits).
   - WHY: The ICI optical network operates in 128-byte flits. Quantizing dynamic
     bucket sizes to multiples of 128 keys (1,024 bytes = 8 flits) eliminates
     partial-flit tail latency and hardware padding overheads.

None of the recommendations alter the use case, problem formulation, benchmark
