3. ARCHITECTURAL FINDINGS & RESOLUTION SUMMARY
================================================================================

1. Direct uint64 in Pallas & TPU v6e Register Constraints:
   - Issue: Mosaic TPU lowers with `NotImplementedError: 64-bit types are not supported`
     because TPU v6e vector registers ($v0..$v31) are 32-bit.
   - Fix: Generate 32-bit high and low words in VMEM using Pallas, write them directly
     into target bucket dimensions, and fuse 64-bit packing at the JAX XLA boundary.

2. Zero-Copy Layout (Eliminated 8.4 GB Transpose):
   - Issue: Interleaved layout required `jnp.swapaxes(0, 1)`, forcing an 8.4 GB out-of-place
     strided memory copy in HBM.
   - Fix: Reordered tensor dimensions to `(TILES_PER_BUCKET, NUM_CHIPS, KEYS_PER_TILE)`
     and performed All-to-All on axis 1. Reshape to `(TILES_PER_BUCKET, NUM_CHIPS * KEYS_PER_TILE)`
     became a zero-cost pointer alias.

3. Clean Coordination Teardown:
   - Issue: Asymmetric exit between pod 1 and pod 0 caused coordinator barrier timeout
     (`DEADLINE_EXCEEDED`) and SIGABRT crash.
   - Fix: Explicit `jax.distributed.shutdown()` synchronized across all worker pods before
     pod 0 enters artifact hold.

4. Compiler / XLA Flags:
   - Issue: Passing TPU-specific flags in `XLA_FLAGS` failed with unknown flag errors.
   - Fix: Dynamically probed `libtpu.so` in entrypoint bash script and exported
     `--xla_tpu_enable_latency_hiding_scheduler=true --xla_tpu_enable_async_all_to_all=true`
     via `LIBTPU_INIT_ARGS`.

5. Transfer-While-Sort Pipelining (Zero-Copy Tuple Return):
   - Issue: Retaining all sorted chunks and calling `jnp.concatenate` required an extra
     7.81 GiB buffer reservation, exceeding available device memory headroom.
   - Fix: Emitted chunks as a tuple `tuple(sorted_chunks)` with double-buffered
     pre-fetching. XLA writes chunks directly to output memory locations, keeping peak
     temporary buffers below 1.95 GiB while achieving 87.5% pipeline stage concurrency.


4. DETAILED ROOT-CAUSE ANALYSIS: PERFORMANCE PARITY (SEQUENTIAL VS. PIPELINED)
================================================================================

Why did the 8-stage Transfer-While-Sort Pipelining exhibit nearly identical
steady-state runtime (~2.2369 s) compared to Sequential Execution (~2.2334 s)?

The live telemetry and XProf metrics reveal three architectural factors:

1. Asymmetry Between Network Transfer (5%) and Local VPU Sort Compute (95%):
   - Total data transferred across the cluster: 67.11 GB (8.39 GB / chip).
   - Over the TPU v6e ICI interconnect running at 619 - 685 GB/s, the entire
     All-to-All collective takes only ~0.098 s to 0.108 s across the 8 chips.
   - In contrast, Phase 2 local bitonic sorting takes ~2.13 s.
   - In each chip, 1,000 bucket rows of 1,048,576 keys (2^20) are sorted.
     A 2^20-element bitonic sorting network requires:
       Stages = 20 * (20 + 1) / 2 = 210 comparison stages.
       Operations per row = 210 * (1,048,576 / 2) = 110,100,480 compare-and-swaps.
       Operations per chip = 1,000 rows * 110.1M = 110.1 billion compare-and-swaps.
       Memory Access = ~119 GiB of streaming read/write operations per chip.
   - Because communication is only ~4.3% of the total execution time, even 100%
     perfect hiding of communication latency behind sort compute yields a theoretical
     maximum runtime reduction of ~0.10 s.

2. HBM Memory Controller Contention (Concurrent DMA vs. VPU Streaming):
   - Sequential Mode: ICI DMA writes incoming packets to HBM in isolation (~0.10 s).
     Once complete, the VPU executes the sorting kernel with uncontended, dedicated
     access to the 1,640 GB/s HBM memory controllers.
   - Pipelined Mode: The ICI DMA engine actively writes incoming chunk packets to
     HBM concurrently while the VPU streams through 119 GiB of data for bitonic
     sorting.
   - Simultaneous memory bus arbitration between DMA write channels and VPU
     streaming access introduces ~10-30 ms of memory latency jitter, largely
     offsetting the ~98 ms of overlapped communication time.

3. Inter-Pod Collective Barrier Jitter (1 vs. 8 Network Synchronizations):
   - Sequential Mode: Executes a single continuous All-to-All DMA across the 2 pods.
   - Pipelined Mode: Dispatches 8 distinct chunked All-to-All collectives.
   - Each collective incurs an inter-pod software and hardware synchronization
     barrier. Multiplying the collective invocations 8-fold adds micro-barrier
     jitter across the distributed cluster.


5. HARDWARE SCALING ANALYSIS: INCREASING TILE SIZE & TOTAL INTEGER VOLUME
================================================================================

Can we increase the tile size / number of integers to generate and sort?
Answer: YES, ABSOLUTELY. The telemetry proves that the 8 TPU v6e cluster is
operating well below its memory capacity and network saturation limits.

1. Available Hardware Headroom:
   - HBM Memory Headroom: TPU v6e has 31.25 GiB allocatable HBM per chip.
     Sequential execution peaked at 15.63 GiB (50.0% usage).
     Pipelined execution peaked at 9.77 GiB (31.3% usage).
     Between 15.6 GiB and 21.5 GiB of HBM is completely free on every chip.
   - Network Headroom: ICI transfer consumes only ~0.098 s at 685 GB/s.
     The interconnect is active for less than 5% of the total pipeline duration.
   - VMEM Scratchpad Headroom: The 2D Pallas tile footprint is ~1-2 MiB, utilizing
     under 2% of the 128 MiB physical VMEM scratchpad per TensorCore.

2. Two Dimensional Approaches to Scale Problem Size:
   Formula: Total Keys = NUM_CHIPS (8) * TILES_PER_BUCKET * (TILE_ROWS * TILE_COLS)

   Approach A: Scale Bucket Depth (TILES_PER_BUCKET) - [RECOMMENDED]:
   - Keeps tile shape at (128, 1024) = 131,072 keys.
   - Keeps local sort row at exactly N = 2^20 = 1,048,576 keys (8 MiB/row),
     which is the optimal hardware configuration for VMEM bitonic sorting without
     memory spilling.
   - Scale to 1,500 tiles -> 12.58 billion keys (100.66 GB cluster dataset).
   - Scale to 1,800 tiles -> 15.10 billion keys (120.80 GB cluster dataset).
   - Critical Value of Pipelining: At 1,800 tiles, sequential mode requires
     2 * 14.06 GiB = 28.12 GiB peak HBM (risking OOM under XLA fragmentation).
     Pipelining breaks the transfer into chunks, requiring only ~15.5 GiB peak HBM,
     enabling safe execution at 120+ GB scales.

   Approach B: Scale Tile Dimensions (TILE_ROWS / KEYS_PER_TILE):
   - Increase TILE_ROWS from 128 to 256 -> 262,144 keys/tile (2 MiB/tile).
   - Each bucket row now contains 8 * 262,144 = 2,097,152 keys (2^21 = 16 MiB).
   - 16 MiB working set fits comfortably within the 128 MiB VMEM scratchpad.
   - Bitonic sort comparison stages increase from 210 to 231 stages (21 * 22 / 2).
   - Total keys double to 16.78 billion keys (134.22 GB cluster dataset).
