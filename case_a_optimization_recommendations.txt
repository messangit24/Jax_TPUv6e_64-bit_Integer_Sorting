================================================================================
  TPU v6e BENCHMARK OPTIMIZATION RECOMMENDATIONS: CASE A (EQUAL BUCKETS)
  Sandia National Laboratories ISx (Integer Sort eXtreme) Specification
================================================================================

1. DIRECT uint64 IN PALLAS & VMEM ARCHITECTURAL CONSTRAINTS
--------------------------------------------------------------------------------
Bottleneck:
  In the baseline implementation, Phase 1 generated two separate 32-bit arrays
  (hi_2d and lo_2d) through Pallas, wrote both out to HBM (4.2 GB each), read
  them back into JAX, and bit-packed them into a uint64 array (8.4 GB).
  This caused ~25.2 GB of HBM traffic and required ~12 GB of temporary HBM buffers.

Architectural Analysis on TPU v6e (Trillium):
  Testing direct in-VMEM 64-bit integer generation via Pallas exposed a hardware
  and compiler constraint:
    `NotImplementedError: 64-bit types are not supported`
    (in `jax/_src/pallas/mosaic/lowering.py: if new_dtype.itemsize == 8`)
  The TPU v6e Vector Processing Unit (VPU) register file consists of 32-bit vector
  registers (VREGs $v0..$v31) and does not natively support 64-bit vector arithmetic
  or shifts in VMEM.

Zero-Overhead Resolution:
  Generate high and low 32-bit components in VMEM, emit them directly via Pallas
  into the optimized zero-copy layout, and fuse 64-bit packing at the JAX XLA
  boundary directly into the target buffer. This eliminates all intermediate
  shuffling and aligns memory for zero-copy downstream consumption.


2. ZERO-COPY LAYOUT (ELIMINATE 8.4 GB HBM TRANSPOSE)
--------------------------------------------------------------------------------
Bottleneck:
  The original tensor layout placed the destination chip dimension first:
    `keys_2d.shape = (NUM_CHIPS, TILES_PER_BUCKET, KEYS_PER_TILE)`
  Running `all_to_all(split_axis=0, concat_axis=0)` stacked received data such that
  bucket keys were interleaved across chips. Reordering required:
    `tiled_buckets = jnp.swapaxes(received, 0, 1).reshape(...)`
  `jnp.swapaxes(0, 1)` forced XLA to perform an out-of-place 8.4 GB strided memory
  transpose in HBM before sorting could commence.

Optimization:
  Adopt a bucket-first tensor layout:
    `keys_2d.shape = (TILES_PER_BUCKET, NUM_CHIPS, KEYS_PER_TILE)`
  Execute ICI All-to-All along dimension 1:
    `received = jax.lax.all_to_all(keys_2d, split_axis=1, concat_axis=1)`
  After this collective, `received[t, :, :]` already contains all keys for bucket `t`
  stored contiguously in row-major memory order. Reshaping to
  `(TILES_PER_BUCKET, NUM_CHIPS * KEYS_PER_TILE)` becomes a zero-copy pointer reshape,
  completely eliminating the 8.4 GB HBM transpose copy.


3. CLEAN COORDINATION TEARDOWN
--------------------------------------------------------------------------------
Bottleneck:
  In multi-pod distributed JAX execution (2 pods, 8 TPU chips), pod 1 finished
  its workload and exited Python immediately. Pod 0 remained alive executing
  `time.sleep(600)` to preserve profiling artifacts (/tmp/xprof, /tmp/xla_dump).
  When pod 1 exited, JAX's internal `atexit` coordination shutdown timed out waiting
  for pod 0 (`DEADLINE_EXCEEDED: Barrier timed out. Id: Shutdown... # tasks: 1/2`).
  This triggered a fatal crash (`SIGABRT`), core dump, and kept `/dev/vfio/0` busy,
  preventing clean redeployment.

Optimization:
  Explicitly synchronize coordination shutdown across all worker pods using:
    `jax.distributed.shutdown()`
  Both pods cleanly negotiate disconnection before pod 0 holds open for telemetry
  and log extraction. This prevents coordinator deadline aborts and releases TPU
  hardware interfaces gracefully.


4. COMPILER / XLA FLAGS FOR LATENCY HIDING & ASYNC COLLECTIVES
--------------------------------------------------------------------------------
Analysis:
  TPU v6e contains independent execution hardware blocks:
    - ICI DMA Controllers: handle inter-chip data movement across the optical network.
    - VPU (Vector Processing Unit): handles bitonic sorting and ALU math.
  By default, XLA can schedule collective communication and compute sequentially
  unless async collective transformations and latency-hiding schedulers are active.

Optimization:
  Dynamically probe `libtpu.so` and pass optimization flags through `LIBTPU_INIT_ARGS`:
    `--xla_tpu_enable_latency_hiding_scheduler=true`
    `--xla_tpu_enable_async_all_to_all=true`
    `--xla_jf_dump_llo_text=true`
  This enables XLA to break `all-to-all` into asynchronous start/done primitives
  and schedule independent computation between them.


5. COMMUNICATION / SORT PIPELINING (TRANSFER WHILE SORT)
--------------------------------------------------------------------------------
Bottleneck in Sequential Phase 2:
  Phase 2 transfers 100% of the dataset, then sorts 100% of the dataset:
    T_total = T_comm + T_sort ≈ 1.0 s + 1.2 s = 2.23 s
  During communication, the VPU is 100% idle.
  During sorting, the ICI DMA engines are 100% idle.

Pipelined Architecture:
  Divide `TILES_PER_BUCKET` into K pipeline stages / chunks (e.g., K = 4):
    Each chunk = `TILES_PER_BUCKET // K` tiles.
  Execute in a pipelined double-buffered schedule:
    1. Prefetch Chunk 0 via ICI All-to-All.
    2. For step k = 0 to K - 2:
         - Launch ICI All-to-All for Chunk k + 1 (DMA engine active).
         - Simultaneously sort Chunk k on the VPU (VPU active).
    3. Drain and sort the final Chunk K - 1 on the VPU.
    4. Concatenate sorted chunks along the bucket dimension.

Performance Impact:
  Execution time drops toward `max(T_comm, T_sort) + latency_overhead`, reducing
  Phase 2 latency from ~2.23 s down toward ~1.2 – 1.4 s (1.6x – 1.8x speedup).
  Additionally, peak working memory for sort buffers is reduced by K-fold.


6. SUMMARY OF BENCHMARK FIDELITY
--------------------------------------------------------------------------------
All five optimizations strictly preserve the Sandia ISx benchmark contract:
  - Identical 64-bit integer pseudo-random distribution.
  - Identical bucket destination bit prefixes.
  - Identical inter-chip routing and local sorting order.
  - Strict global validation: monotonic row check, tile boundary check, chip boundary
    check (`max(Chip_i) <= min(Chip_{i+1})`), and 64-bit global checksum verification.
